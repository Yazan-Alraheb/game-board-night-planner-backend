# Issue #10: Chat and Messaging migration

## Scope and prerequisites

Baseline: `main` commit `66c5a68`, after Issue #9 and before Issue #10.
The existing `public.conversations`, `public.conversation_members`, and
`public.messages` tables must match those baseline models. Existing `public.users`
and `public.game_nights` tables and their referenced IDs must exist. Issue #9's
friendship changes are assumed deployed; these scripts never read or change
friendships. No Alembic or initialization changes are introduced.

The upgrade adds the normalized private pair columns, cascading user foreign
keys, pair uniqueness/check constraints, the message length constraint, and two
query indexes. The new foreign keys use the names PostgreSQL generates for a
fresh SQLAlchemy `create_all()` schema (`conversations_private_user_low_id_fkey`
and `conversations_private_user_high_id_fkey`), so migrated and freshly created
databases match. It renames the existing single-column game-night uniqueness
constraint after identifying it by its definition, not its autogenerated name.
Its supporting index is reused. Existing PostgreSQL `timestamptz` columns do not
need conversion for `UTCDateTime`. There are no server timestamp defaults to add.

These are one-time, ordered scripts, not idempotent repair scripts. They reject
an already-upgraded or partially-upgraded schema, unexpected additional indexes,
custom triggers, row security, and conflicting definitions. This intentionally
requires review of schema drift instead of guessing. Equivalent indexes under
other names cause an abort, not creation of duplicate indexes. They do not audit
the complete schema of unrelated tables or attempt to repair Issue #9.

The scripts use PostgreSQL catalogs and PL/pgSQL and are intended for PostgreSQL
14 or later. Confirm the exact deployment version in an isolated rehearsal.
Use the table owner (or an appropriately privileged migration role); do not run
with a role that cannot inspect and alter all affected objects. The target schema
is explicitly `public`; other schemas require a reviewed adaptation.

## Conflict handling and preservation

Before backfill, the upgrade checks:

- Exact baseline column types/nullability, serial ID defaults, check/primary/unique
  constraints, foreign key definitions, and index definitions.
- Every private conversation has exactly two distinct existing members. The
  baseline membership primary key already prevents duplicate member rows.
- No two private conversations normalize to the same user pair.
- No orphaned participant, message, or game-night references exist.
- No duplicate non-null game-night links exist.
- No existing message exceeds 2,000 PostgreSQL characters (not bytes).

Private-pair and membership conflicts and long messages report up to 20 affected
IDs/groups. Other schema/reference errors describe the failing category. Fixes
require a separately reviewed data decision (see "Diagnosing a failed upgrade");
the migration never merges chats, truncates messages, or deletes history. Unfriended private pairs are retained.
The only row updates populate the two new columns on private conversations;
group pairs remain null. Messages, memberships, and friendships are unchanged.

All changes run in a single transaction. Locks on users/game nights prevent
referenced-row deletion, and exclusive chat-table locks prevent concurrent
membership or message changes between validation and DDL. `lock_timeout` is
5 seconds per lock wait; `statement_timeout` is 5 minutes per statement. These
are blocking maintenance scripts, not an online/concurrent-index migration.
Budget maintenance time and storage for scans, indexes, and the backfill; adjust
timeouts only after rehearsal. A failed statement must roll back the transaction.

## Rehearse before deployment

No migration has been executed against any PostgreSQL database as part of this
implementation. Parser checks cannot verify catalog behavior, locks, permissions,
or execution plans. Rehearse on a disposable PostgreSQL database matching the
server version, with a sanitized copy or schema/data fixture of the baseline.
Never point a rehearsal command at the shared development database.

Two rehearsals are required, in this order. Neither one modifies the team
database; the only step that touches it is the read-only schema export below.

### 1. Schema preflight (structural compatibility)

The repository has no record of how the team database was created, and the
upgrade accepts only the exact baseline schema that SQLAlchemy `create_all()`
produces from the `66c5a68` models. The preflight proves this before any
maintenance window by running the upgrade against a copy of the team schema.

**Export (authorized teammate only).** Someone with approved access to the team
database exports the schema without any rows. `pg_dump` only reads; prefer a
read-only role. Use a PostgreSQL 17 client (`pg_dump` must not be older than the
server). Store the file outside the repository and never commit it; it contains
no message data, but it describes the production schema.

```powershell
pg_dump --schema-only --no-owner --no-privileges --dbname="<approved read-only connection string>" --file="<outside-repo>\gamenight_schema_baseline.sql"
```

**Restore into a disposable PostgreSQL 17 database.** Use a throwaway container
with no volume and no published port, so nothing can reach it and it disappears
when removed. Do not reuse the `compose.yaml` service, its volume, or port 5433.

```powershell
docker run --rm -d --name gamenight-migration-rehearsal -e POSTGRES_PASSWORD="<throwaway local value>" postgres:17-alpine
docker cp "<outside-repo>\gamenight_schema_baseline.sql" gamenight-migration-rehearsal:/tmp/baseline.sql
docker cp migrations/010_chat_messaging_upgrade.sql gamenight-migration-rehearsal:/tmp/upgrade.sql
docker cp migrations/010_chat_messaging_rollback.sql gamenight-migration-rehearsal:/tmp/rollback.sql
docker exec gamenight-migration-rehearsal psql -X -v ON_ERROR_STOP=1 -U postgres -c "CREATE DATABASE gamenight_rehearsal"
docker exec gamenight-migration-rehearsal psql -X -v ON_ERROR_STOP=1 -U postgres -d gamenight_rehearsal -f /tmp/baseline.sql
```

Wait a few seconds after `docker run` for the server to accept connections. If
the restore fails (for example on a role, extension, or ownership statement),
stop and review the dump instead of editing it until it passes. Without a dump,
an equivalent baseline can be recreated by running SQLAlchemy `create_all()`
from the `66c5a68` models against this disposable database only. That proves
the scripts work but not that the team schema matches.

**Rehearse.** Run upgrade, rollback, and upgrade again, checking each exit code:

```powershell
docker exec gamenight-migration-rehearsal psql -X -v ON_ERROR_STOP=1 -U postgres -d gamenight_rehearsal -f /tmp/upgrade.sql; $LASTEXITCODE
docker exec gamenight-migration-rehearsal psql -X -v ON_ERROR_STOP=1 -U postgres -d gamenight_rehearsal -f /tmp/rollback.sql; $LASTEXITCODE
docker exec gamenight-migration-rehearsal psql -X -v ON_ERROR_STOP=1 -U postgres -d gamenight_rehearsal -f /tmp/upgrade.sql; $LASTEXITCODE
```

Each must print `0`. After the first upgrade, run the queries under "Verify
afterward" against `gamenight_rehearsal`. A failure means the team schema
differs from the baseline; diagnose it with the queries under "Diagnosing a
failed upgrade", run against the rehearsal copy. Remove the container afterward:

```powershell
docker rm -f gamenight-migration-rehearsal
```

**Limit:** a schema-only rehearsal verifies structural compatibility only. Its
tables are empty, so every data check passes trivially: member counts,
duplicate private pairs, message length, and orphaned references are not
tested, nor are backfill duration or lock behavior under realistic volume.

### 2. Data-bearing rehearsal

Before applying the migration to a database that contains chat rows, repeat the
rehearsal with data, using one of:

- **Synthetic data (preferred):** load the restored schema with fixtures
  covering the cases below. No real user data is involved.
- **A protected backup:** restore a full backup only into an isolated,
  access-restricted, disposable environment. It contains private messages,
  email addresses, and password hashes: never commit it, share it, or keep it
  after the rehearsal.

Include successful upgrade/rollback with empty tables and historical private and
group chats, messages, and friendships. Also test zero/one/three private members,
duplicate private pairs, 2,001-character messages, missing constraints, extra or
renamed equivalent indexes, and an already-applied migration. Every rejected
upgrade must leave the original schema/data intact. Test an unusual original
game-night constraint name/comment and verify exact restoration on rollback.
Run the upgrade again after rollback. Hold a conflicting lock in another test
session and confirm timeout leaves no partial migration.

If the populated team database may contain conflicts, an authorized operator
can run the read-only diagnostic queries below to size the problem first; they
contain no `INSERT`, `UPDATE`, `DELETE`, or DDL.

## Verify afterward

Compare row counts and historical contents with the backup. No conversation,
participant, message, user, or friendship should disappear or change, apart from
the new derived pair fields. The following query must return no rows:

```sql
SELECT c.id
FROM public.conversations c
LEFT JOIN (
    SELECT conversation_id, count(*) AS member_count,
           min(user_id) AS low_id, max(user_id) AS high_id
    FROM public.conversation_members GROUP BY conversation_id
) m ON m.conversation_id = c.id
WHERE (c.type = 'private' AND (
    coalesce(m.member_count, 0) <> 2
    OR c.private_user_low_id IS DISTINCT FROM m.low_id
    OR c.private_user_high_id IS DISTINCT FROM m.high_id
)) OR (c.type = 'group' AND (
    c.private_user_low_id IS NOT NULL OR c.private_user_high_id IS NOT NULL
));
```

Inspect definitions and validity (all constraints must be validated and indexes
valid/ready), and confirm the named Issue #10 objects match the current models:

```sql

WHERE conrelid IN ('public.conversations'::regclass,
                  'public.conversation_members'::regclass,
```

## Diagnosing a failed upgrade

A failed upgrade rolls back completely; nothing needs undoing. Match the error
message to a category below. Every query here is read-only. Prefer running them
on a rehearsal copy; on the team database, only an authorized operator may run
them. The queries avoid selecting message content so private text is not
exposed during diagnosis.

**The migration must not be changed to delete, merge, truncate, or rewrite
conflicting data, and its checks must not be weakened to make it pass.** Each
"next step" below is a decision for the team, not an instruction. Any
corrective data change needs its own written SQL, a review, approval, and a
fresh backup, and must be rehearsed before it is run. Then rerun the unchanged
upgrade.

### Private conversations without exactly two members

Error: `Private conversations must have exactly two members`.

```sql
SELECT c.id, c.created_at, count(m.user_id) AS member_count,
       array_agg(m.user_id ORDER BY m.user_id)
           FILTER (WHERE m.user_id IS NOT NULL) AS member_ids,
       (SELECT count(*) FROM public.messages msg
        WHERE msg.conversation_id = c.id) AS message_count
FROM public.conversations c
LEFT JOIN public.conversation_members m ON m.conversation_id = c.id
WHERE c.type = 'private'
GROUP BY c.id, c.created_at
HAVING count(m.user_id) <> 2
ORDER BY c.id;
```

Next steps to decide on:

- **One member** usually means the other user was deleted; the baseline cascade
  removed the membership but kept the conversation. Either keep the history by
  changing the conversation's `type` to `'group'`, or delete the conversation
  after the remaining user's history is exported or explicitly abandoned.
- **Three or more members** are a group in practice. Changing `type` to
  `'group'` preserves every member and message.
- **Zero members** cannot be read by anyone. If `message_count` is 0, deleting
  the row loses nothing; otherwise decide whether the history must be archived.

### Duplicate private conversations for the same pair

Error: `Duplicate private pairs`.

```sql
WITH pairs AS (
    SELECT c.id, c.created_at, min(m.user_id) AS low_id, max(m.user_id) AS high_id
    FROM public.conversations c
    JOIN public.conversation_members m ON m.conversation_id = c.id
    WHERE c.type = 'private'
    GROUP BY c.id, c.created_at
    HAVING count(*) = 2
)
SELECT p.low_id, p.high_id, p.id AS conversation_id, p.created_at,
       (SELECT count(*) FROM public.messages msg
        WHERE msg.conversation_id = p.id) AS message_count
FROM pairs p
WHERE (p.low_id, p.high_id) IN (
    SELECT low_id, high_id FROM pairs GROUP BY low_id, high_id HAVING count(*) > 1
)
ORDER BY p.low_id, p.high_id, p.created_at, p.id;
```

Issue #10 allows one private conversation per pair. Options: pick one
conversation to keep (for example the oldest) and move the others' messages
into it, which is a merge and needs approval; or change the extra
conversations' `type` to `'group'` so all histories stay separate. Either way,
the two users must keep access to every message they could previously read.

### Messages longer than 2,000 characters

Error: `Messages exceed 2000 characters`.

```sql
SELECT id, conversation_id, user_id, created_at,
       length(content) AS characters, octet_length(content) AS bytes
FROM public.messages
WHERE length(content) > 2000
ORDER BY id;
```

Lengths are PostgreSQL characters, not bytes, matching the new constraint and
the API limit. Options: split each message into several messages of at most
2,000 characters with the same sender and timestamp ordering, which preserves
all text; or truncate only after the full original is archived and the change
is approved. Never truncate silently.

### Missing baseline constraints or unexpected schema changes

Errors: `Expected ordinary public table`, `Unexpected columns/types/nullability`,
`Unexpected defaults/sequence`, `Unexpected or missing primary/unique/check
constraints`, `Unexpected, duplicate, or missing indexes`, `Unexpected or
missing foreign key`, `Unexpected foreign keys`, `Custom triggers or row
security`, `Orphaned conversation/member/message references`, or `Duplicate
game-night conversation links`.

```sql
SELECT table_name, column_name, data_type, character_maximum_length,
       is_nullable, column_default, is_identity
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN ('conversations', 'conversation_members', 'messages')
ORDER BY table_name, column_name;

SELECT conrelid::regclass AS table_name, conname, contype, convalidated,
       pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid IN ('public.conversations'::regclass,
                   'public.conversation_members'::regclass,
                   'public.messages'::regclass)
ORDER BY 1, 2;

SELECT indrelid::regclass AS table_name, indexrelid::regclass AS index_name,
       indisvalid, indisready, pg_get_indexdef(indexrelid) AS definition
FROM pg_index
WHERE indrelid IN ('public.conversations'::regclass,
                   'public.conversation_members'::regclass,
                   'public.messages'::regclass)
ORDER BY 1, 2;

SELECT tgrelid::regclass AS table_name, tgname, pg_get_triggerdef(oid)
FROM pg_trigger
WHERE tgrelid IN ('public.conversations'::regclass,
                  'public.conversation_members'::regclass,
                  'public.messages'::regclass)
  AND NOT tgisinternal;

SELECT oid::regclass AS table_name, relrowsecurity, relforcerowsecurity
FROM pg_class
WHERE oid IN ('public.conversations'::regclass,
              'public.conversation_members'::regclass,
              'public.messages'::regclass);
```

If a table is missing entirely, the `::regclass` casts fail; the first query
still shows which tables exist. Compare the results with the baseline that
`create_all()` produces from the `66c5a68` models. Constraint names marked
"generated" may differ between databases:

```sql
CREATE TABLE conversations (
    id SERIAL NOT NULL,
    type VARCHAR NOT NULL,
    game_night_id INTEGER,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (id),                                              -- generated
    CONSTRAINT ck_conversation_type CHECK (type IN ('private', 'group')),
    CONSTRAINT ck_private_conversation_no_game_night
        CHECK (type != 'private' OR game_night_id IS NULL),
    UNIQUE (game_night_id),                                        -- generated
    FOREIGN KEY (game_night_id) REFERENCES game_nights (id) ON DELETE CASCADE
);
CREATE INDEX ix_conversations_id ON conversations (id);
CREATE TABLE conversation_members (
    conversation_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    PRIMARY KEY (conversation_id, user_id),                        -- generated
    FOREIGN KEY (conversation_id) REFERENCES conversations (id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
);
CREATE TABLE messages (
    id SERIAL NOT NULL,
    conversation_id INTEGER NOT NULL,
    user_id INTEGER NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (id),                                              -- generated
    CONSTRAINT ck_message_content_not_empty CHECK (length(trim(content)) > 0),
    FOREIGN KEY (conversation_id) REFERENCES conversations (id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
);
CREATE INDEX ix_messages_id ON messages (id);
```

Next steps: find out where the difference came from (manual change, another
tool, an older model version) before changing anything. A missing or
`NOT VALID` constraint may mean existing rows violate it, so check the data
before restoring the constraint. Repairing the schema is a separate, reviewed
migration; afterwards rerun the schema preflight. Do not edit the upgrade's
expected-schema checks to match an unreviewed schema.

### Existing Issue #10 columns, constraints, or indexes

Errors: usually `Unexpected columns/types/nullability on conversations` or
`Unexpected or missing primary/unique/check constraints`.

```sql
SELECT 'column' AS kind, table_name || '.' || column_name AS object_name
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'conversations'
  AND column_name IN ('private_user_low_id', 'private_user_high_id')
UNION ALL
SELECT 'constraint', conrelid::regclass || '.' || conname
FROM pg_constraint
WHERE conrelid IN ('public.conversations'::regclass, 'public.messages'::regclass)
  AND conname IN ('uq_conversation_game_night', 'uq_conversation_private_pair',
                  'ck_conversation_private_pair', 'ck_message_content_length',
                  'conversations_private_user_low_id_fkey',
                  'conversations_private_user_high_id_fkey')
UNION ALL
SELECT 'index', name
FROM unnest(ARRAY['public.ix_conversation_members_user_conversation',
                  'public.ix_messages_conversation_created_id']) AS name
WHERE to_regclass(name) IS NOT NULL
ORDER BY 1, 2;

-- Migration 010 provenance marker, written only by this upgrade.
SELECT conname, obj_description(oid, 'pg_constraint') AS comment
FROM pg_constraint
WHERE conrelid = 'public.conversations'::regclass AND contype = 'u';
```

Next steps:

- **All Issue #10 objects present, and the comment is a JSON marker with
  `"migration": "010_chat_messaging"`:** the upgrade has already been applied.
  Do not run it again.
- **All objects present, no marker:** the schema was most likely created by
  `create_all()` from the Issue #10 models. It needs no migration, and the
  rollback script does not apply to it (it refuses to run without the marker).
- **Only some objects present:** the upgrade is a single transaction and cannot
  leave a partial result, so these objects were added some other way. Stop and
  find out how. Do not drop them to make the upgrade pass without review and
  approval.

## Roll back (operator only)

Stop Issue #10 workers, take a fresh backup, and run:

```powershell
psql -X --dbname="<approved connection string>" -v ON_ERROR_STOP=1 -f migrations/010_chat_messaging_rollback.sql
```

The rollback validates the Issue #10 schema first. It removes only the new pair
columns and their constraints, the message-length constraint, and the two new
indexes. It does not delete conversations, memberships, messages, or friendships.
The upgrade stores the original game-night constraint name/comment as JSON in
that constraint's comment; rollback restores both. Preserve this migration
marker until rollback is no longer needed. Missing/corrupt provenance or external
dependencies cause failure instead of a guessed rename or cascading deletion.

After verifying the baseline schema and preserved data, deploy the previous
application version before resuming traffic. That version does not depend on the
new pair columns or constraint names. Pair values are derived data and can be
reconstructed on a later upgrade. Schema changes made after Issue #10 require a
new rollback review; do not force this script through unexpected drift.

## Offline validation performed

Both complete scripts were parsed with `pglast`, including their PL/pgSQL blocks.
Isolated SQLAlchemy metadata compiled from both `main` and the current model
sources confirmed the changed columns, constraint/index counts and names, and
unchanged PostgreSQL timestamp types. Static assertions checked transaction and
timeout boundaries, validation-before-backfill ordering, and absence of row
removal statements. These checks create no database connections or tables and
are not a substitute for executing the rehearsal cases above on PostgreSQL.

After the foreign keys were renamed to PostgreSQL's generated names, both
scripts and every SQL block in this README were parsed again with `pglast` 7.
An offline comparison of the `66c5a68` and current SQLAlchemy metadata confirmed
that the upgrade adds exactly the changed columns, constraints (names, columns,
`ON DELETE CASCADE`, check expressions), and indexes (including `DESC` order),
and that the rollback drops exactly those objects.
